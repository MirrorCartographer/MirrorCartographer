## Purpose

This document makes the project's origin, contribution model, evidence boundaries, and technical lineage independently inspectable. It is a factual project record, not a legal determination of copyright ownership, employment status, patent inventorship, or the terms of any third-party service.

## Origin and direction

Mirror Cartographer originated in the user's work on symbolic and emotional self-mapping, reflective interaction, and the problem of preserving meaning across nonlinear human experience. The recovered 2024–2025 conversation archive and Canvas documents show iterative product definition, interface requirements, symbolic taxonomies, reflection workflows, and later expansion into research and systems architecture.

The project lead supplied the problem framing, product direction, requirements, domain concepts, interaction preferences, design decisions, testing feedback, prioritization, and acceptance judgments. These contributions are distinguishable from code generated by AI assistants and from services or libraries supplied by third parties.

Attribute code at the artifact or commit level whenever commit history, source comments, or conversation records support it. Where exact line-level attribution is unavailable, record authorship as mixed or unverified.

## AI assistance disclosure

AI assistants were used as programming, research, drafting, and debugging aids. Historical conversations document code generation and iteration before the release of dedicated coding-agent products. The presence of AI assistance does not erase the project lead's role in defining the system, directing implementation, selecting requirements, evaluating outputs, and deciding what to retain.

The specific model, model version, API route, and execution environment must be reported only when supported by contemporaneous metadata or logs. A conversation with a model does not prove that the model executed code; source code that contains an API call does not by itself prove that the call succeeded.

## Evidence hierarchy

1. **Strongest:** reproducible tests, CI run records, deployment checks, immutable commits, signed releases, and original files with hashes.
2. **Strong:** source code, complete Canvas document snapshots, dated conversation-export records, and captured service configuration.
3. **Supporting:** screenshots, email outputs, archived user reports, and contemporaneous implementation notes.
4. **Context only:** retrospective recollection, unexecuted plans, speculative architecture, and assistant-generated summaries.

Every public claim should link to the relevant artifact and state its verification level. Plans are not implementations; source presence is not runtime proof; synthetic data are not field results.
